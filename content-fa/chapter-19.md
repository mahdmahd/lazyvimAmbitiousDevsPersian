# فصل ۱۹. راهنمای جامع پیکربندی افزونه‌ها

## [فصل ۱۹. راهنمای جامع پیکربندی LazyVim](#_comprehensive_guide_to_lazyvim_configuration)

پیکربندی پایهٔ افزونه را در فصل ۵ پوشش دادیم و وقتی لازم داشتم افزونهٔ خاصی را پیکربندی کنم جزئیات برخورد با وضعیت‌های پیچیده‌تر را دادم، اما در سراسر کتاب پراکنده است.

این فصل با کمی مرور همهٔ آن شروع می‌کند و بعد سعی می‌کند ابزارهای لازم برای پیدا کردن و پیکربندی افزونه‌های دیگر نئوویم که به‌صورت Lazy Extras در دسترس نیستند را به شما بدهد.

### [۱۹.۱. دایرکتوری افزونه‌ها](#_plugins_directory)

همان‌طور که در فصل ۵ پوشش دادیم، افزونه‌ها با مدیر افزونهٔ `Lazy.nvim` مدیریت می‌شوند. پیکربندی شده تا هر فایل `.lua` در `lua/plugins` پوشهٔ پیکربندی‌تان را خودکار لود کند. معمولاً این `~/.config/nvim/lua/plugins` خواهد بود که `~` دایرکتوری خانگی شماست. اما اگر از متغیر محیطی `NVIM_APPNAME` استفاده کنید، آن وقت `~/.config/$NVIM_APPNAME/lua/plugins` خواهد بود.

فایل‌های لوا در این دایرکتوری همیشه باید جدول لوا برگردانند. پس ساختاری مثل این خواهند داشت:

فهرست ۸۰. افزونهٔ خالی

```
return {

}
```

این جدول لوا می‌تواند یا مشخصات افزونه‌ای یا جدولی شامل چند مشخصات افزونه در جدول لوای خودشان را داشته باشد. مثلاً ساختار یا این خواهد بود:

فهرست ۸۱. تک‌افزونهٔ پایه

```
return {
  "username/plugin",
  opts = {...},
  keys = {...}
  ...
}
```

برای یک مشخصات تک‌افزونه، یا:

فهرست ۸۲. چند افزونه در یک فایل

```
return {
  {
    "username/plugin",
    opts = {...},
    keys = {...}
  },
  {
    "username2/plugin2",
    ...
  }

}
```

شخصاً معمولاً هر افزونه را در فایل خودش می‌گذارم تا وقتی از میان‌بر `<Space>fc` استفاده می‌کنم راحت جست‌وجوشان کنم. اما وقتی وجود یک افزونه اقتضا می‌کند پیکربندی افزونهٔ دیگری را تغییر دهم از قالب چندافزونه‌ای استفاده می‌کنم.

### [۱۹.۲. آبشاری شدن مشخصات افزونه](#_plugin_specifications_cascade)

هر افزونه‌ای را می‌توان چند بار در پیکربندی‌تان مشخص کرد و LazyVim همه را با هم ادغام می‌کند. چند مورد هست که این مفید است:

- بعضی دوست دارند کلیدبندی‌ها را در ناحیه‌ای جدا از گزینه‌ها و پیکربندی افزونه پیکربندی کنند.

- گاهی می‌خواهید پیکربندی اصلی افزونه‌تان در یک فایل باشد و بعد افزونهٔ مرتبط دوم اوررایدهایی برای آن افزونه پیکربندی کند.

- (رایج‌ترین) LazyVim خیلی افزونه‌ها را با پیش‌فرض‌های معقولی ازپیش‌پیکربندی می‌کند، اما گاهی می‌خواهید آن پیش‌فرض‌ها را با کلیدبندی‌ها یا گزینه‌های ترجیحی‌تان اورراید کنید.

### [۱۹.۳. مشخصات افزونه](#_plugin_specification)

ساده‌ترین مشخصات افزونه فقط جدولی شامل تک‌رشته‌ای با نام کاربری و ریپوی گیت‌هاب جداشده با `/` است. گاهی همین همهٔ چیزی است که لازم دارید، مخصوصاً برای افزونه‌های ویم‌اسکریپت. اگر افزونهٔ موردنظر روی گیت‌هاب میزبانی نمی‌شود، می‌توانید این آرگومان اول را حذف کنید و یا `dir=/path/to/a/folder` یا `url=https://domain.com/path/to/plugin` را پاس دهید.

اگر لازم است افزونه‌تان را به نسخه یا برنچ گیت خاصی پین کنید، می‌توانید `branch` یا `tag` یا `commit` یا `version` را پاس دهید. برای افزونه‌های میزبانی‌شده روی گیت‌هاب، مقادیر این مشخص‌کننده‌های نسخه را می‌توانید روی گیت‌هاب پیدا کنید. احتمالاً فقط به‌ندرت از این استفاده می‌کنید، چون عادی است که برنچ `main` افزونه را نصب کنید. اما اگر بدانید تغییر اخیر در افزونه‌ای برایتان مشکل ایجاد می‌کند، یا اگر بخواهید قابلیت لبهٔ خونینی را امتحان کنید که هنوز مرج نشده، می‌خواهید یکی از این‌ها را تنظیم کنید.

تقریباً دو دوجین گزینه هست که می‌توانید به مشخصات افزونهٔ `Lazy.nvim` پاس دهید، همه در [https://lazy.folke.io/spec](https://lazy.folke.io/spec) مستند شده‌اند. بعضی‌شان را در فصل ۵ بحث کردیم، یعنی `enabled` و `opts` و `keys`. حالا به چندتای دیگر می‌پردازیم.

### [۱۹.۴. متدهای چرخهٔ حیات افزونه](#_plugin_lifecycle_methods)

چند گزینه هست که در زمان‌های مختلف در چرخهٔ حیات افزونه‌ای فراخوانی می‌شوند. فقط به‌ندرت لازم است این‌ها را مشخص کنید، اما می‌توانند برای کنترل زمان اجرای کد خیلی مفید باشند، مخصوصاً اگر سعی می‌کنید دستورهای نصب «پیکربندی خام» را به پیکربندی `Lazy.nvim` پورت کنید.

#### [۱۹.۴.۱. بیلد](#_build)

گزینهٔ `build` یک بار وقتی افزونه نصب یا به‌روز می‌شود صدا زده می‌شود و در استارتاپ یا اجرای عادی نئوویم صدا زده نمی‌شود. مثالی از آن را در پیکربندی `smart-splits` در فصل ۹ دیدیم. در آن مثال، رشته‌مسیری به اسکریپت شلی که با افزونه عرضه می‌شود پاس دادیم. هر بار که افزونه نصب یا ارتقا یابد، آن دستور بیلد اجرا می‌شود و مطمئن می‌شود اسکریپت‌های مرتبط Kitty نصب‌اند. علاوه بر مسیر رشته‌ای، `build` می‌تواند یکی از این‌ها هم باشد:

- تابع لوایی که مشخصات افزونه را به‌عنوان تنها آرگومانش می‌پذیرد.

- مسیر به فایل لوای دلخواه.

- رشتهٔ «rockspec» که بستهٔ `luarocks` را بیلد می‌کند. `Luarocks` مدیر بسته و ایندکسی برای ماژول‌های لوا مثل `pypi` و `npm` یا `crates` در اکوسیستم‌های پایتون، جاوااسکریپت و راست به‌ترتیب است.

- رشته‌ای که با `:` شروع می‌شود که دستور ویم دلخواهی اجرا می‌کند.

- فهرستی از یک یا چندتای بالا.

به‌عنوان مصرف‌کنندهٔ افزونه، احتمالاً فقط تابع `build` را مشخص می‌کنید اگر مستندات افزونه به شما بگوید.

#### [۱۹.۴.۲. شروع (Init)](#_init)

گزینهٔ `init` در استارتاپ برنامه اجرا می‌شود، پس برای کوتاه نگه‌داشتن زمان استارتاپ، بهتر است از آن اجتناب کنید مگر کاملاً ضروری. تابع لوایی با تک‌آرگومانی که هر مشخصاتی برای آن افزونه نگه می‌دارد می‌پذیرد. (مشخصاً، نمونه‌ای از [LazyPlugin](https://github.com/folke/lazy.nvim/blob/main/lua/lazy/types.lua) است).

واقعاً هیچ‌وقت لازم نداشتم `init` را در هیچ‌کدام از پیکربندی‌های افزونه‌هایم مشخص کنم. معمولاً اگر لازم باشد افزونه در استارتاپ اجرا شود، از `lazy=false` استفاده می‌کنم تا کل چیز را در استارتاپ پیکربندی کند. می‌توانم ببینم `init` مفید باشد اگر راه‌اندازی‌های دوقدمهٔ مشروعی باشند، اما در تجربه‌ام، همهٔ آن‌ها در افزونه‌هایی‌اند که LazyVim از طرف من مدیریتشان می‌کند، پس هیچ‌وقت لازمش نداشتم.

#### [۱۹.۴.۳. پیکربندی (Config)](#_config)

گزینهٔ `config` همان است که به احتمال زیاد مشخصش می‌کنید، اما سعی کنید فقط وقتی سراغش بروید که گزینه‌های دیگر تمام شده باشند. هر وقت افزونه لود می‌شود صدا زده می‌شود، که بسته به نحوهٔ پیکربندی‌اش ممکن است در استارتاپ باشد یا فقط وقتی اول استفاده می‌شود.

اولین چیزی که باید دربارهٔ `config` بفهمید رفتار پیش‌فرضش است اگر مشخصش نکنید.

استاندارد بالفعل در افزونه‌های لوامحور فراهم کردن تابع `setup` است که تک‌آرگومانی می‌پذیرد که جدولی از گزینه‌ها برای آن افزونه است. اکثریت عظیم افزونه‌هایی که می‌بینید دستورهایی در `README` دارند که کدی شبیه این بنویسید:

فهرست ۸۳. فراخوانی Setup غیر-LazyVim

```
require('pluginName').setup({key = value, key2 = value2...})
```

به شما می‌گویند این را در `init.lua` بگذارید. این‌ها دستورهای خوبی‌اند اگر از LazyVim استفاده نمی‌کنید، اما برای ما نیست.

تابع پیش‌فرض `config` که `Lazy.nvim` فراهم می‌کند این کد را خودکار اجرا می‌کند اگر مشخصات‌تان شامل `opts` باشد. پس کد بالا همیشه باید به چیزی مثل این پورت شود:

فهرست ۸۴. گزینه‌های LazyVim

```
return {
  'username/plugin',
  opts = {key = value, key2 = value2}
}
```

زیر کاپوت، اگر `opts` را در مشخصات افزونه بدهید، تابع `config` کد `.setup` را برایتان صدا می‌زند.

این چیز فوق‌العاده‌ای است چون LazyVim ادغام خودکار جدول‌های `opts` را انجام می‌دهد اگر مشخصات چندگانه برای همان افزونه در جاهای مختلف داده باشید. اگر `config` را اورراید کنید، نمی‌توانید به همین راحتی از این رفتار ادغام بهره ببرید.

اما اگر افزونه‌ای که پیکربندی می‌کنید غیراستاندارد است یا لازم است کد اضافه‌ای وقتی در حال استارتاپ است اجرا کنید، باید خودتان `config` را مشخص کنید.

تابع `config` همیشه تابع لوایی است که دو آرگومان می‌پذیرد. اولی همان مشخصات `LazyPlugin` است که `init` می‌گیرد. دومی جدول `opts` است که `Lazy.nvim` برایتان ساخته، احتمالاً با ادغام `opts` از چند تعریف.

جای اصلی که این مشکل می‌شود وقتی است که می‌خواهید پیکربندی پیش‌فرض LazyVim برای افزونه‌ای را سفارشی کنید و آن پیکربندی پیش‌فرض `config` را اورراید می‌کند.

برخلاف `opts` و `keys`، فقط یک تابع `config` صدا زده می‌شود (آخرین لودشده). پس اگر برای افزونه‌ای `config` مشخص کنید، مال LazyVim اجرا نمی‌شود.

معمولاً این پیکربندی‌های اوررایدشده را می‌توان با استفادهٔ عاقلانه از `opts` یا `keys` تغییر داد، اما اگر لازم باشد کارهای امری انجام دهید که با هرچه LazyVim فراهم می‌کند فرق دارد، احتمال زیادی هست که کل پیکربندی آن افزونه را از وب‌سایت [https://lazyvim.org](https://lazyvim.org) در پیکربندی شخصی‌تان کپی کنید.

هرچند نتیجهٔ عالی نیست، هنوز بهتر از وقتی است که اصلاً از LazyVim استفاده نکنید، چون آن وقت باید کل پیکربندی را از صفر بنویسید به‌جای کپی و تغییر منبع مورداعتماد برای زیرمجموعهٔ کوچکی از افزونه‌ها.

### [۱۹.۵. تغییر گزینه‌ها درجا](#_modifying_options_in_place)

«ادغامی» که LazyVim روی `opts` انجام می‌دهد اگر جدول لوا بدهید ممکن است همیشه کار درست را نکند، مخصوصاً با جدول‌های تودرتو یا اگر بخواهید کلیدی را حذف کنید. گاهی بهتر است `opts` را به‌صورت تابع لوا مشخص کنید. LazyVim نسخهٔ «قبلی» جدول `opts` را به‌عنوان ورودی پاس می‌دهد و تابع باید آن را *درجا* تغییر دهد. مثال عالی افزودن ورودی به منوی داشبورد است:

فهرست ۸۵. تغییر گزینه‌ها با تابع

```
return {
  "snacks.nvim",
  opts = function(_, opts)
    table.insert(
      opts.dashboard.preset.keys,
      7,
      { icon = "S", key = "S", desc = "Select Session", action = require("persistence").select }
    )
  end,
}
```

این‌جا `opts` به‌صورت تابعی مشخص شده که دو آرگومان می‌گیرد و ما دومی را تغییر می‌دهیم که جدول لوایی است که LazyVim می‌سازد تا به `config` پاس دهد.

### [۱۹.۶. پیکربندی گزینه‌های غیرافزونه‌ای](#_configuring_non_plugin_options)

ویم ویرایشگر بسیار قابل‌پیکربندی است و نئوویم حتی بیشتر. بیش از سیصد گزینه در خروجی `:help option-list` هست. پیکربندی پیش‌فرض ویم برای بیشتر این‌ها خوب است، هرچند چندتایی پیش‌فرض‌های مسخره به دلایل تاریخی دارند. نئوویم چندتایشان را درست کرده و LazyVim تقریباً یک‌سوم‌شان را تنظیم می‌کند تا تجربهٔ خارج‌ازجعبه تقریب چیزی باشد که بیشتر توسعه‌دهنده‌های مدرن می‌خواهند.

اما احتمالاً هنوز می‌خواهید چند گزینه را به سلیقه‌تان تغییر دهید. این معمولاً در فایل `lua/config/options.lua` انجام می‌شود. LazyVim این فایل را به‌طور پیش‌فرض لود می‌کند.

برای هر گزینه‌ای، *احتمالاً* می‌خواهید فیلد `vim.opt.<optionname>` را تنظیم کنید. `vim.opt` جدول لوای خاصی است که اجازه می‌دهد با تنظیمات ویم به‌مثابه…​ خب، جدول لوای خاصی تعامل کنید. اگر دنبال تنظیم ویمی می‌گردید و چیزی می‌بینید که می‌گوید باید `:set option=value` را صدا بزنید، آن کار می‌کند، اگر بخواهید موقتاً انجامش دهید. اما اگر بخواهید تنظیم را برای دفعهٔ بعد که نئوویم را استارت می‌کنید ذخیره کنید، باید به `vim.opt.option = value` ترجمه‌اش کنید.

*گاهی*، و بعد از ۲۵ سال استفاده از ویم *هنوز* دقیق مطمئن نیستم کی، باید به‌جایش `vim.g.<optionname> = value` را تنظیم کنید. `g` در این مورد یعنی سراسری (global). اگر دستوری ببینید که متغیری مثل `let g:varname = value` را تنظیم می‌کند، شاید لازم باشد از `vim.g.varname = value` استفاده کنید. بعضی گزینه‌ها ذاتاً سراسری‌اند در حالی که بعضی فقط به بافر فعلی اعمال می‌شوند *مگر* این‌که `g` را مشخص کنید. بعضی افزونه‌ها، مخصوصاً افزونه‌های قدیمی غیر-لوا، با متغیرهای سراسری پیکربندی می‌شوند و این نحوی است که برای آن‌ها هم استفاده می‌کنید.

به‌طور کلی، از `vim.opt` استفاده کنید مگر این‌که در مستندات یا کدی که از آن کپی می‌کنید `vim.g` یا `g:` ببینید.

### [۱۹.۷. تنظیم طرح رنگ (تم)](#_setting_the_colour_scheme_theme)

ویم دو گزینه برای تنظیم طرح رنگ دارد و می‌توانند به شکل‌های غیرمنتظره‌ای تعامل کنند.

اول، می‌توانید پس‌زمینهٔ پنجره‌تان را یا `dark` یا `light` تنظیم کنید. می‌توانید این تنظیم را در زمان اجرا با کلیدبندی `<Space>ub` زیر منوی «Ui» تاگل کنید. **معمولاً** وقتی پس‌زمینه را تاگل می‌کنید، طرح رنگ رنگ‌های پیش‌زمینه را برای تطبیق با پس‌زمینهٔ انتخاب‌شده تغییر می‌دهد، اما این همیشه قابل‌اعتماد نیست. گاهی حتی طرح رنگ را به طرح مرتبطی که وقتی پس‌زمینه روشن است مناسب‌تر است تغییر می‌دهد. مثلاً اگر `catpuccin-mocha` فعال باشد و پس‌زمینه‌تان را به روشن تغییر دهید، `catpuccin-latte` طرح رنگ انتخاب‌شده می‌شود.

اگر می‌خواهید پس‌زمینه را دائمی تغییر دهید، `vim.opt.background = "light"` یا `vim.opt.background = "dark"` را در فایل `options.lua` تنظیم کنید.

برای تغییر به طرح رنگ کاملاً متفاوت، از `<Space>uC` استفاده کنید که `C` بزرگ است. این انتخاب‌گری با همهٔ طرح‌های رنگ نصب‌شدهٔ فعلی بالا می‌آورد. نئوویم با چند طرح رنگ پیش‌فرض عرضه می‌شود و LazyVim چند واریاسیون `Catppuccin` و `Tokyo Night` (پیش‌فرض) را اضافه می‌کند. مزیت این طرح‌های رنگ نسبت به آن‌هایی که نئوویم فراهم می‌کند این است که کلی گروه هایلایت اضافه برای افزونه‌های مختلفی که LazyVim نصب می‌کند دارند.

اگر می‌خواهید طرح رنگ را دائمی تغییر دهید، باید به‌صورت `opt` روی افزونهٔ `LazyVim/LazyVim` تنظیم شود. من طرح رنگ `catpuccin` را ترجیح می‌دهم، پس فایل `plugins/core.lua` دارم که این شکلی است:

فهرست ۸۶. پیکربندی طرح رنگ

```
return {
  {
    "LazyVim/LazyVim",
    opts = {
      colorscheme = "catppuccin",
    },
  },
}
```

اما اگر بخواهید طرح رنگ را به چیزی تنظیم کنید که به‌طور پیش‌فرض با LazyVim عرضه نمی‌شود، *همچنین* باید افزونه‌ای که آن طرح رنگ را عرضه می‌کند نصب کنید. مثلاً حالت آمادهٔ محبوب `gruvbox` را می‌توان این‌طور نصب کرد:

فهرست ۸۷. طرح رنگ شخص ثالث

```
return {
  { "ellisonleao/gruvbox.nvim" },
  {
    "LazyVim/LazyVim",
    opts = {
      colorscheme = "gruvbox",
    },
  },
}
```

|  | وقتی دنبال طرح‌های رنگ جدید می‌گردید، سعی کنید ریپوهای خوش‌نگهداری را پیدا کنید که «پشتیبانی تری‌سیتر» دارند و گروه‌های هایلایت برای همهٔ افزونه‌هایی که مرتب استفاده می‌کنید فراهم می‌کنند (از جمله آن‌هایی که با LazyVim عرضه می‌شوند). می‌توانید طرح‌های رنگ را در فهرست [Awesome Neovim](https://github.com/rockerBOO/awesome-neovim/) پیدا کنید. |

### [۱۹.۸. بارگذاری تنبل](#_lazy_loading)

LazyVim خودکار افزونه‌ها را به‌جای زمان استارتاپ برنامه، هنگام نیاز به‌صورت تنبل (lazy) لود می‌کند. این می‌تواند میلی‌ثانیه‌هایی از زمان استارتاپ‌تان کم کند (آن منبع خیلی‌خیلی‌ارزشمند).

LazyVim می‌داند افزونه را هر وقت کدش `require` شود یا وقتی هر کدام از کلیدبندی‌های مشخص‌شده در آرایهٔ `keys` فشرده شوند لود کند. این معمولاً دقیقاً وقتی است که می‌خواهید لود شود. اما اگر با افزونه‌هایی مواجه شدید که آن‌طور که انتظار می‌رود کار نمی‌کنند، شاید لازم باشد پیکربندی بارگذاری تنبل را دست‌کاری کنید.

اول، سعی کنید `lazy = false` را به مشخصات افزونه اضافه کنید. این مطمئن می‌شود افزونه در استارتاپ لود می‌شود. اگر افزونه بعد از افزودن آن کار کرد، دو گزینه دارید:

- فقط `lazy = false` را بگذارید و به روزتان برسید.

- میکرو-بهینه‌سازی کنید تا سعی کنید افزونه را وادارید در زمان درست به‌صورت تنبل لود شود.

بیشتر، گزینهٔ اول را توصیه می‌کنم. میکرو-بهینه‌سازی در زمینهٔ بهینه‌سازی افزونه‌ها برای مصرف عمومی منطقی است. نگه‌دارنده‌های افزونه ممکن است در بسته‌هایشان از آن استفاده کنند و قطعاً نگه‌دارنده‌های دیسترو مثل خود Folke وقت زیادی رویش می‌گذارند. اما برای شما احتمالاً نمی‌ارزد.

افزونه را با `lazy` فعال و غیرفعال اجرا کنید و زمان استارتاپ را در داشبورد بررسی کنید. اگر تفاوتی ایجاد کرد که می‌خواهید حلش کنید، ادامه بخوانید.

اگر افزونه‌ای فقط باید برای فایل‌تایپ‌های خاصی مشخص شود، آن وقت کلید `ft` را به مشخصات اضافه کنید. این کلید رشته یا فهرستی از رشته‌ها که نشان‌دهندهٔ فایل‌تایپ‌اند می‌پذیرد. (برای گرفتن فایل‌تایپ بافر فعلی، `:set ft<Enter>` را تایپ کنید).

اگر در عوض افزونه فقط باید وقتی دستورهای خاصی صدا زده می‌شوند لود شود، فهرستی از رشته‌ها با نام‌های دستور را زیر کلید `cmd` مشخص کنید.

همچنین می‌توانید `event` نئوویمی مشخص کنید که باید لود افزونه را تحریک کند. خیلی زیادند تا در این کتاب فهرستشان کنم، پس شما را به `:help events` ارجاع می‌دهم. رایج‌ترین‌ها برای تحریک لود افزونه `BufEnter` و `BufRead` و `BufWrite` می‌شوند.

### [۱۹.۹. پیکربندی خاص فایل‌تایپ](#_filetype_specific_configuration)

اگر لازم باشد چیزی را پیکربندی کنید که برای فایل‌تایپ خاصی اجرا شود، به تابع `nvim_create_autocmd` نیاز دارید. از نظر فنی می‌توانید این فراخوانی را هرجا بگذارید، از جمله `init.lua` یا `config` یا `init` افزونهٔ خاصی، اما رسم LazyVim این است که در فایل `lua/config/autocmds.lua` بگذاریدشان.

واقعاً خودم فقط یک `autocmd` دارم چون LazyVim کار خیلی خوبی در پیکربندی رفتارهای خاص فایل‌تایپ برایم می‌کند (معمولاً با اکسترای مناسب `lang.*` LazyVim). آن دستور این شکلی است:

فهرست ۸۸. اتوکامندهای خاص فایل‌تایپ

```
vim.api.nvim_create_autocmd({ "BufRead", "BufNewFile" }, {
pattern = "\*.svx",
command = "setlocal filetype=markdown",
})
```

آرگومان اول جدول لوای بدون‌کلید از نام‌های رویداد رشته‌ای است؛ در این مورد هر وقت فایلی بسازم یا بخوانم، اتوکامند اجرا می‌شود. رویدادهای دیگری هم هست که می‌توانید استفاده کنید، اما معمولاً فقط به این دو نیاز دارید مگر این‌که افزونهٔ خودتان را بنویسید (برای فهرست کامل `:help autocmd-events` را ببینید).

آرگومان دوم شامل گزینه‌های اتوکامند است. در این مورد `pattern` را می‌آورم که رجکس ویم برای نوع فایلی است که می‌خواهم مچ کنم. مشخصاً گفتم «رجکس ویم» تا `\*` عجیب را توجیه کنم، چنان‌که در فصل ۱۲ بحث شد.

در این مورد از کلید `command` برای اجرای دستوری هر وقت فایل `*.svx` را می‌خوانم استفاده می‌کنم. در عوض می‌توانید کلید `callback` را مشخص کنید که مقدارش تابع لوایی است که هر وقت رویداد رخ می‌دهد صدا زده می‌شود.

### [۱۹.۱۰. پیکربندی هرپروژه](#_per_project_configuration)

گاهی، می‌خواهید پیکربندی LazyVim سفارشی برای پروژهٔ خاصی داشته باشید. مثلاً بیشتر پروژه‌های تایپ‌اسکریپت من در `Svelte` هستند که یعنی نمی‌توانم (هنوز) از لینتر/فرمتر استثنایی `biome` برایشان استفاده کنم. یعنی در این ریپوها از `prettier` برای فرمت استفاده می‌کنم. مشخصات افزونهٔ `extend-conform.lua` من این شکلی است:

فهرست ۸۹. Prettier در پیکربندی پیش‌فرض

```
return {
  {
    "stevearc/conform.nvim",
    opts = {
      formatters_by_ft = {
        ["typescript"] = { "prettier" },
        ["markdown"] = { "prettier" },
        ["yaml"] = { "prettier" },
        ["svelte"] = { "prettier" },
      },
    },
  },
}
```

اما برای سرورهای API تایپ‌اسکریپتم، **می‌توانم** از `Biome` استفاده کنم و می‌خواهم پیکربندی‌ام را فقط برای آن پروژه‌ها اورراید کنم.

LazyVim این را خیلی ساده می‌کند: فقط فایل `.lazy.lua` در پروژه‌تان بسازید. می‌تواند هر مشخصات افزونهٔ معتبری برگرداند و بعد از لود شدن هر افزونهٔ دیگری صدا زده می‌شود و آن‌ها را بازنویسی می‌کند. پس سرور API مدل `Hono` من فایل `.lazy.lua` دارد که این شکلی است:

فهرست ۹۰. فایل `.lazy.lua` خاص پروژه

```
return {
  {
    "stevearc/conform.nvim",
    opts = {
      formatters_by_ft = {
        ["typescript"] = { "biome" },
      },
    },
  },
}
```

می‌توانید انتخاب کنید این را با پروژه‌تان کامیت کنید یا بسته به استانداردهای پروژه `.gitignore` کنید.

### [۱۹.۱۱. رسپی‌های LazyVim](#_lazyvim_recipes)

LazyVim باکمک درخواست‌شده‌ترین قابلیت‌ها را به‌صورت رسپی در [صفحهٔ خانگی](https://www.lazyvim.org/configuration/recipes) جمع می‌کند. بیشتر این‌ها را می‌توان مستقیم در هر فایلی در پوشهٔ `lua/plugins` کپی کرد. یادتان باشد `return` جلویشان بگذارید تا هر جدولی که می‌دهند اکسپورت شود.

بیشتر رسپی‌ها فقط مجموعه‌ای از `opts` پیشنهادی برای تحریک رفتار موردنظر فراهم می‌کنند. این `opts` همیشه خاص افزونه‌اند و باید فایل راهنما یا `README` افزونه را ببینید تا بفهمید چه می‌کنند.

### [۱۹.۱۲. خلاصه](#_summary_19)

این فصل همه دربارهٔ پیکربندی LazyVim بود. خیلی‌اش ممکن است مرور مثال‌هایی باشد که در سراسر کتاب وقتی افزونه‌هایی برای پشتیبانی قابلیت‌های خاص اضافه می‌کردم استفاده کردم. اما می‌خواستم مطمئن شوم پوششی در یک جا هست برای وقتی که می‌خواهید چیزها را نگاه کنید.
