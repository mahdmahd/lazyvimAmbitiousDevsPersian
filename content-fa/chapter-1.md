# فصل ۱. مقدمه و نصب

## [فصل ۱. مقدمه و نصب](#_introduction_and_installation)

این کتاب برای همهٔ توسعه‌دهندگانی نوشته شده است که مجذوب قدرتی شده‌اند که ویرایش مُدال (Modal editing) می‌تواند به همراه داشته باشد، اما از حجم عظیم پیکربندی که حتی آموزش‌های مقدماتی این حوزه به آن‌ها تحمیل می‌کنند، یا ترسیده‌اند یا خسته شده‌اند.

حدس می‌زنم شما کاربر ویژوال استودیو کد (Visual Studio Code) باشید (ویرایشگر فوق‌العاده‌ای که خودم چند سال از آن استفاده کردم)، اما ممکن است از محیط‌های توسعهٔ یکپارچه و ویرایشگرهای کد متعدد دیگری به سمت ویرایش مُدال آمده باشید. احتمالاً نام ویم (Vim) را شنیده‌اید و چیزی باعث شده بخواهید آن را امتحان کنید.

### [۱.۱. چرا ویم](#_why_vim)

ویم سابقه‌ای *بسیار* کهن دارد. در اوایل دههٔ ۹۰ میلادی به‌عنوان بهبودی بر ویرایشگر (بسیار) قدیمی‌تر Vi ساخته شد که خود در دههٔ ۷۰ میلادی نوشته شده بود. نام «Vim» در واقع مخفف «Vi, improved» یعنی «Vi بهبودیافته» است. سلف آن، Vi مخفف «Visual» به معنای «دیداری» است، چون نسخه‌ای تکامل‌یافته از یک تجربهٔ ویرایش خطی غیردیداری قدیمی‌تر به نام `ed` از سال ۱۹۷۱ بود.

|  |  |
| --- | --- |
|  | جالب است بدانید `ed` به‌نحوی هنوز روی سیستم‌های یونیکس مدرن موجود است و اگر از محیط مک‌اواس یا لینوکس استفاده می‌کنید، احتمالاً می‌توانید با تایپ `ed` در هر ترمینالی به آن دسترسی پیدا کنید. (اگر اشتباهاً آن را امتحان کردید، `Control-D` شما را دوباره خارج می‌کند). شما اکنون به‌اندازهٔ من دربارهٔ `ed` می‌دانید و باور کنید، نمی‌خواهید بیشتر بدانید. |

ممکن است با نسخهٔ دیگری از `ed` به نام `sed`، یعنی «ویرایشگر جریانی (stream editor)» نیز آشنا باشید. تا امروز هنوز برای تغییر متن در خط لولهٔ شل (shell pipeline) استفاده می‌شود.

دستور `ed` همچنین **توسعه** (**ex**tended) داده شد تا ویرایشگر خطی دیگری به نام `ex` ساخته شود که دیگر واقعاً استفاده نمی‌شود، مگر (به‌طور گسترده) به‌عنوان زیرحالت (submode) ویم. در واقع، اگر نئوویم را نصب کنید و `ex` را در خط فرمان خود تایپ کنید، نمونه‌ای بسیار محدود از نئوویم دریافت می‌کنید که فقط از دستورهای `ex` پشتیبانی می‌کند.

پس این شجره‌نامهٔ پرشاخ‌وبرگی است، اما صرف قدمت خانوادگی پیش‌بینی‌کنندهٔ خوبی برای کیفیت نیست، همان‌طور که هر «بازماندهٔ نسل چهارمی» گواهی می‌دهد.

دلایل زیادی برای استفاده از هر ویرایشگری وجود دارد، اما دلایلی که برای ویم برجسته‌اند عبارت‌اند از:

مزایای سلامت (Health Benefits)

این دلیل اصلی برای من است. در اوایل دوران کاری‌ام زیاد از ویم استفاده می‌کردم، هرچند مثل بسیاری از توسعه‌دهندگان، وقتی VS Code در سال ۲۰۱۵ آمد به آن مهاجرت کردم. زمان زیادی را پای صفحه‌کلید می‌گذرانم و تا سال ۲۰۲۰ چنان از آسیب فشار مکرر (RSI) ناتوان شده بودم که شش ماه فقط با صدا کدنویسی می‌کردم (مقاله‌ای وبلاگی دربارهٔ این موضوع مرا مشهورتر از انتظارم کرد). دوستی پیشنهاد کرد به ویرایش مُدال برگردم و تفاوت عظیمی ایجاد کرد. اکثریت عظیم کلیدهای ویم نیازی به نگه‌داشتن هم‌زمان چند کلید با یک دست ندارند، چیزی که سندرم تونل کارپال را واقعاً تشدید می‌کند.

کارایی (Performance)

بیشتر آی‌دی‌ای‌ها نوعی لایه یا افزونهٔ «شبیه‌سازی vi» دارند که اجازه می‌دهد بدون مهاجرت کامل به ویرایشگری جدید، از برخی مزایای سلامتی ویرایش مُدال بهره‌مند شوید. اما انتظار برای بالا آمدن VS Code و بارگذاری همهٔ افزونه‌هایی که می‌شناسید و دوست دارید، برای بسیاری به تمرینی مراقبه‌ای (یا فرصتی برای بازگشت به اسکرول بی‌پایان) تبدیل شده است. در مقابل، وقتی پیکربندی LazyVim خودم را بارگذاری می‌کنم، به‌طور مفیدی به من می‌گوید که بارگذاری چقدر طول کشیده است: ۵۶.۹۸ میلی‌ثانیه. برای چشمان کند و انسانی من، آنی است.

سرعت توسعه‌دهنده (Developer Velocity)

این مورد بحث‌برانگیز و سلیقه‌ای است. هر ابزاری تنها به‌اندازهٔ صاحب‌هنری خوب است که آن را به کار می‌گیرد و من قطعاً کدنویس‌های ممتازی می‌شناسم که با پیکربندی VS Code، ایمکس یا جت‌برینز خود واقعاً پرواز می‌کنند. با این حال، واقعاً باور دارم که یک پیکربندی ویمِ دقیق‌کوک‌شده می‌تواند از همهٔ آن‌ها پیشی بگیرد.

اکوسیستم باز (Open Ecosystem)

احترام زیادی برای نحوهٔ برخورد مایکروسافت با نرم‌افزار متن‌باز از زمان روی کار آمدن نادلا قائلم، اما VS Code نشانه‌های فزاینده‌ای از قفل شدن اختصاصی (proprietary lock-in) نشان می‌دهد (به‌ویژه با یکپارچه‌سازی‌های هوش مصنوعی‌اش). در مقابل، اکوسیستم نئوویم جامعه‌ای باز و پرجنب‌وجوش است و هر هفته افزونه‌های نوآورانه‌ای می‌رسند که در VS Code هرگز به فکر ساختن‌شان نمی‌افتند.

### [۱.۲. چرا به‌طور خاص نئوویم](#_why_neovim_specifically)

اگر تصمیم بگیرید از ویم استفاده کنید، به‌سرعت کشف می‌کنید که دو گونهٔ مدرن وجود دارد: Vim و Neovim. هر دو نوادگان مستقیم همان کد متن‌باز ویم دههٔ ۹۰ هستند. Neovim در سال ۲۰۱۴ از Vim منشعب (فورک) شد با چشم‌انداز بازسازی و مدرن‌سازی کدبیس و مجموعهٔ ویژگی‌ها.

هر دو فعالانه نگهداری می‌شوند و هر دو پتانسیل این را دارند که صیقلی و مدرن حس شوند، هرچند رسیدن به آن پتانسیل کمی پیکربندی می‌طلبد. هر کدام اکوسیستم افزونه‌ای (Plugin) بسیار قدرتمندی دارند، اما نئوویم یک ویژگی کشنده (killer feature) دارد: زبان برنامه‌نویسی لوا (Lua) را برای توسعهٔ افزونه (و پیکربندی) علاوه بر VimScript بومی که نسخهٔ خواهرش استفاده می‌کند، معرفی کرده است.

لوا به‌خودی‌خود نئوویم را ذاتاً بهتر از ویم نمی‌کند. با این حال، جایی که بیشتر افزونه‌های ویم روی نئوویم هم اجرا می‌شوند، عکس آن همیشه صادق نیست و افزونه‌های لوا درجه‌یکی وجود دارند که فقط با نئوویم کار می‌کنند.

برای اهداف این کتاب، تصمیم شما از قبل برایتان گرفته شده است: توزیع LazyVim که این کتاب دربارهٔ آن است فقط با Neovim کار می‌کند.

### [۱.۳. معرفی LazyVim](#_introducing_lazyvim)

نقطه‌ضعف اصلی هم Vim و هم Neovim این است که هرچند توانایی ارائهٔ همان تجربهٔ ویرایش مدرن (یا بهتر) هر آی‌دی‌ای دیگری را دارند، اما از ابتدا این‌طور نیستند. ویم سنت طولانی حفظ سازگاری با ابزار قدیمی `vi` را دارد و نئوویم فقط اندکی از آن سنت فاصله گرفته است. وقتی برای اولین بار نئوویم را نصب می‌کنید، تجربهٔ ویرایش کد نسبتاً بی‌روحی دریافت می‌کنید.

وقتی در سال ۲۰۲۰ پس از عادت کردن به قابلیت‌های فوق‌العاده‌ای که VS Code به اکوسیستم ویرایشگر آورده بود، به ویم برگشتم، **دو هفته** طول کشید تا پیکربندی‌ام را به جایی که می‌خواستم برسانم و ماه‌ها بعد از آن مدام آن را دست‌کاری می‌کردم. حدود ۳۰۰ خط Vimscript شد که بعداً به حدود ۲۵۰ خط کد لوا پورت کردم. انصافاً، من به‌طور کلی سفارشی‌ساز پرکاری هستم و پیکربندی VS Code من در واقع از هر دوی آن‌ها طولانی‌تر بود! اما با کمال میل قبول می‌کنم که تجربهٔ خارج‌ازجعبهٔ VS Code خیلی بهتر بود.

به چندین «توزیع (distribution)» به‌اصطلاح نئوویم (راه‌اندازی‌های ازپیش‌پیکربندی‌شده) نگاه کردم. وارد جزئیات مقایسه نمی‌شوم، اما LazyVim با فاصلهٔ زیاد برندهٔ واضح است، عمدتاً چون تجربهٔ خارج‌ازجعبهٔ فوق‌العاده ساده را با سفارشی‌سازی و پیکربندی نسبتاً آسان متوازن می‌کند.

برای شفافیت، LazyVim همان Vim است. تجربهٔ ویرایش یکسان است. تکرار یا نسخهٔ جدیدی از Vim به آن معنا که Neovim هست، نیست. در عوض، LazyVim یک طرز فکر است؛ با توافقی بر سر این‌که بهترین پیکربندی‌های افزونه برای توسعهٔ مدرن چیست شروع می‌شود و پیکربندی‌ای که باعث می‌شود آن‌ها خوب با هم کار کنند (جلوگیری از تداخل کلیدهای میان‌بر افزونه‌های مختلف با یکدیگر یکی از نقاط دردناک اصلی هنگام مدیریت دستی پیکربندی‌های ویرایشگر است).

اما اگر با این طرز فکر وارد استفاده از LazyVim شوید که این تجربه بهتر از هر تجربهٔ ویرایش دیگری خواهد بود که قبلاً با آن کار کرده‌اید و بپذیرید که مقداری از حافظهٔ عضلانی صفحه‌کلید را بازآموزی می‌کنید، خواهید دید که بسیار خوب اندیشیده شده است. به تجربهٔ من، *دقیقاً* همان چیزی است که یک تجربهٔ ویرایش مُدالِ عصر دههٔ ۲۰۲۰ باید باشد.

### [۱.۴. انتخاب ترمینال](#_choosing_a_terminal)

اگر تا اینجا آمده‌اید، احتمالاً فکر می‌کنید آمادهٔ نصب نئوویم هستید. در واقع، هنوز یک تصمیم دیگر هم باقی مانده که باید بگیرید.

نئوویم می‌تواند در بسترهای مختلف زیادی اجرا شود (حتی می‌توانید آن را داخل ویژوال استودیو کد اجرا کنید!) به‌طور پیش‌فرض برنامه‌ای ترمینالی است، اما رابط‌های گرافیکی (GUI) زیادی هم موجودند. تقریباً همهٔ آن‌ها را امتحان کرده‌ام و صادقانه بگویم، فکر نمی‌کنم رابط‌های گرافیکی مزیت ذاتی نسبت به اجرای مستقیم نئوویم در ترمینال داشته باشند.

اتصال نئوویم به چند GUI را خیلی دیرتر در کتاب به‌اختصار بحث می‌کنیم، اما برای شروع، توصیه می‌کنم نئوویم را در ترمینال اجرا کنید. به‌طور مشخص، یک ترمینال خیلی خوب.

برای بهترین تجربهٔ ویرایش ویم، ترمینالی با شتاب GPU می‌خواهید. یعنی چه؟ اساساً یعنی از تراشه‌ای که برای رندر بازی‌های ویدیویی فوتورئالیستیک طراحی شده برای رندر سورس‌کد استفاده خواهید کرد. به‌اندازهٔ استفاده از آن برای هوش مصنوعی منطقی به نظر می‌رسد، نه؟

باید دربارهٔ گزینه‌های زیر خودتان تحقیق کنید، پس از موتور جست‌وجوی محبوب‌تان یا بات چت هوش مصنوعی روز کمک بگیرید تا تصمیم بگیرید:

[Kitty Terminal](https://sw.kovidgoyal.net/kitty/)

ترجیح شخصی من است. آن را خوب مستندسازی‌شده، با پیکربندی آسان و کاملاً پرقابلیت می‌دانم. اگر توصیهٔ مشخصی لازم دارید، با Kitty شروع کنید.

[Alacritty](https://alacritty.org)

احتمالاً برندهٔ سرعت خام است، اما پیکربندی‌اش ناخوشایند است و کم‌قابلیت‌تر است.

[Wezterm](https://wezfurlong.org/wezterm/index.html)

برخی ویژگی‌های خیلی جالب دارد، اما مستنداتش را ناقص یافتم و در به کار انداختن برخی جنبه‌ها مشکل داشتم.

[Windows Terminal](https://github.com/microsoft/terminal?tab=readme-ov-file)

اگر کاربر ویندوز هستید، ادعا می‌کند شتاب GPU دارد، هرچند دیدم نئوویم گاهی در آن بی‌پاسخ می‌شد.

[Warp Terminal](https://www.warp.dev)

اگر سوار قطار Warp شده‌اید و بدون آن نمی‌توانید زندگی کنید، نئوویم داخل آن کار *خواهد* کرد. تجربه را کمی ناهموار یافتم و از ظاهر و حس Warp خوشم نیامد (یا این واقعیت که برای استفاده باید وارد حساب می‌شدم).

پس یک یا چند تا از آن‌ها را نصب کنید تا یکی را که دوست دارید پیدا کنید. اگر بخواهید *می‌توانید* از شبیه‌سازهای ترمینال دیگر استفاده کنید. احتمالاً حتی متوجه پایین‌تر بودن تجربه نمی‌شوید، اما قول می‌دهم اگر بعداً به تجربهٔ شتاب‌گرفته با GPU مهاجرت کنید، *بهبود* را متوجه می‌شوید.

### [۱.۵. راه‌اندازی فونت ترمینال](#_setting_up_your_terminal_font)

LazyVim و افزونه‌هایش در ترمینال زیبا به نظر می‌رسند و تقریباً باور نمی‌کنید که برنامهٔ GUI نیستند. برای این کار، به فونت‌های خاصی وابسته‌اند که کلی گلیف (glyph) برای چیزهای مرتبط با کدنویسی دارند. برجسته‌ترین سودش، دسترسی به آیکون‌هایی است که نوع فایل بازشده را نشان می‌دهند، اما قاب‌های زیبا و ظاهر و حس پنجره‌مانند را هم در ترمینال فراهم می‌کند.

برای بهترین تجربهٔ LazyVim، باید یکی از این فونت‌های خاص را نصب کنید و ترمینال‌تان را برای استفاده از آن پیکربندی کنید. در واقع، حتی اگر کاربر سنگین نئوویم نیستید، باید واقعاً از یکی از این فونت‌ها در ترمینال‌تان استفاده کنید. بسیاری از اپ‌های ترمینال مدرن (عجب عبارتی، ها؟) اگر آن‌ها نصب باشند بهتر به نظر می‌رسند.

برای اطلاعات بیشتر به [Nerd Fonts](https://nerdfonts.com) مراجعه کنید. اگر از Kitty استفاده می‌کنید، کافی است فونت `NerdFontsSymbolsOnly` را نصب کنید و اگر نمادها را در فونت مونوسپیس پیکربندی‌شده‌تان پیدا نکند، به‌طور خودکار از آن فونت می‌گیرد. برای ترمینال‌های دیگر، احتمالاً باید فونت «وصله‌شده (patched)» را همان‌طور که در سایت Nerd Fonts بحث شده نصب و پیکربندی کنید. انتخاب‌های زیادی هست.

می‌توانید از میان بسیاری از محبوب‌ترین فونت‌های برنامه‌نویسی انتخاب کنید. دانلود و نصب آن‌ها خیلی وابسته به سیستم‌عامل است، پس راهنمای سایت Nerd Fonts را می‌گذارم که برایتان توضیح دهد.

### [۱.۶. نصب نئوویم](#_install_neovim)

نئوویم تقریباً همه‌جا که نرم‌افزار می‌تواند نصب شود کار می‌کند و فقط به وابستگی‌های استاندارد سیستم متکی است. مشکل اصلی این است که هر سیستم‌عاملی که استفاده کنید، از این‌همه انتخاب غرق‌شده‌اید!

می‌توانید به [صفحهٔ خانگی Neovim](https://neovim.io/) بروید و دکمهٔ «Install Now» را بزنید تا آخرین دستورالعمل‌ها برای سیستم‌عامل انتخابی‌تان (یا اجباری‌تان) از طرف توسعه‌دهندگان نئوویم را بگیرید.

#### [۱.۶.۱. کدام نسخه را نصب کنم؟](#_which_version_should_i_install)

توسعهٔ نئوویم در مقایسه با چرخهٔ انتشارشان با سرعت فوق‌العاده زیادی اتفاق می‌افتد، پس غیرمعمول نیست که افراد آخرین بیلد شبانه (nightly) را اجرا کنند. فقط به‌ندرت در بیلدهای بریده‌شده از شاخهٔ master در GitHub به باگ برخورده‌ام، پس عموماً امن است. معمولاً وقتی نسخهٔ پایدار جدید می‌آید با آن کار می‌کنم و بعد وقتی به‌روزرسانی افزونه‌ای می‌گوید «اگر از نئوویم nightly استفاده کنی قابلیت باحالی اینجاست»، به‌جایش آخرین بیلد نئوویم را نصب می‌کنم.

پیشنهاد می‌کنم فعلاً با آخرین نسخهٔ پایدار نئوویم شروع کنید که در زمان نگارش 0.11.0 است. اگر ممکن است از نمونه‌های قدیمی‌تر پرهیز کنید. LazyVim تمایل دارد ویژگی‌هایی از نسخهٔ nightly اضافه کند، پس اگر به‌اندازهٔ من دربارهٔ این توزیع هیجان‌زده شوید، مهاجرت به پیش‌انتشار، پیشرفتی کاملاً طبیعی خواهد بود.

#### [۱.۶.۲. ویندوز](#_windows)

در ویندوز، توصیه می‌کنم از زیرسیستم ویندوز برای لینوکس (WSL) استفاده کنید و همهٔ توسعه را در آن انجام دهید. WSL کاملاً خارج از دسترس این کتاب است، اما توسط مایکروسافت و بسیاری از آموزش‌های آنلاین به‌خوبی مستندسازی شده است. وقتی توزیع لینوکس سازگار با WSL را انتخاب کردید، راه‌اندازی کردید و در ترمینال منتخب‌تان اجرا کردید، می‌توانید نئوویم را با دستورالعمل‌های لینوکس زیر نصب کنید.

اگر دلیل یا ترجیحی دارید که روی ویندوز بومی توسعه دهید، آسان‌ترین کار گرفتن نصب‌کنندهٔ MSI از بخش Releases مخزن [neovim/neovim](https://github.com/neovim/neovim/) در GitHub است.

اگر از قبل از Winget، Chocolatey یا Scoop برای مدیریت بسته‌ها روی ماشین ویندوزی‌تان استفاده می‌کنید، در هر کدام بستهٔ Neovim هست.

توجه کنید که اگر از ویندوز بدون WSL استفاده کنید، برای گرفتن پشتیبانی تری‌سیتر (treesitter) (که اساساً به معنای هایلایت نحوی و پشتیبانی ناوبری کد بهتر است) باید کامپایلر C هم نصب کنید. این متأسفانه همیشه کار بدیهی نیست. یک خواننده پیشنهاد می‌کند بسته‌های `neovim` و `zig` (که زنجیره‌ابزار کامپایلر C را شامل می‌شود) را با Scoop نصب کنید. اگر جواب نداد، پیشنهاد می‌کنم مستندات مخزن GitHub [nvim-treesitter/nvim-treesitter](https://github.com/nvim-treesitter/nvim-treesitter) را دنبال کنید، پس اینجا وارد جزئیات نمی‌شوم.

#### [۱.۶.۳. مک‌اواس](#_macos)

بیشتر توسعه‌دهندگان در مک‌اواس از Homebrew استفاده می‌کنند، پس اگر آن را ندارید، توصیه می‌کنم با دنبال کردن دستورالعمل‌های [brew.sh](https://brew.sh/) آن را نصب کنید.

وقتی brew بالا آمد و اجرا شد، دستور `brew install neovim` نئوویم را نصب می‌کند.

اگر می‌خواهید روی لبه زندگی کنید، `brew install --HEAD neovim` آخرین نسخهٔ nightly نئوویم را نصب می‌کند که احتمالاً، اما نه تضمیناً، پایدار است.

تجربهٔ brew را بسیار مهربان‌تر از گزینه‌های دیگر نصب نئوویم در مک‌اواس می‌دانم، پس اگر کاربر Homebrew نیستید، به‌شدت توصیه می‌کنم راه‌اندازی‌اش کنید. ابزارهای متن‌باز دیگری هم هست که وقتی عمیق‌تر وارد سفر LazyVim می‌شویم می‌خواهید نصب کنید و brew آسان‌ترین راه برای گرفتن همه‌شان خواهد بود.

اگر نخواهید از Homebrew استفاده کنید، کارها کمی آزاردهنده‌تر است. تیم توسعهٔ Neovim نصب‌کنندهٔ مک‌اواس نگهداری نمی‌کند، پس باید تاربال را دانلود و استخراج کنید، بعد از جایی روی مسیر سیستم (system path) به باینری لینک دهید. اگر نمی‌دانید هیچ‌کدام از این‌ها یعنی چه، صادقانه بگویم، از Homebrew استفاده کنید، آسان‌تر است!

#### [۱.۶.۴. لینوکس](#_linux)

اگر نئوویم با مدیر بستهٔ پیش‌فرض توزیع‌تان در دسترس نیست، توزیع لینوکس بسیار عجیبی دارید، واقعاً!

پس فقط `sudo pacman -S neovim`، `sudo apt install neovim`، `sudo dnf install neovim` یا دستور مناسب هر مدیر بستهٔ غیرمتعارف دیگری که ترجیح می‌دهید را اجرا کنید.

هرچند برخی توزیع‌ها نسخه‌های به‌طرز دلسردکننده‌ای قدیمی نئوویم را عرضه می‌کنند. اگر نسخهٔ nightly بخواهید، ممکن است دستورالعمل‌ها را در صفحهٔ Releases GitHub `neovim/neovim` پیدا کنید یا مجبور شوید در مستندات توزیع‌تان بگردید.

همچنین در حالتی بعید که توزیع لینوکس‌تان با کامپایلر C عرضه نشده باشد، باید یکی نصب کنید. برای بیشتر توزیع‌ها فقط بستهٔ `gcc` را نصب کنید و آمادهٔ کار خواهید بود.

### [۱.۷. نئوویم خام را امتحان کنید (اگر جرئتش را دارید)](#_try_neovim_raw_if_you_dare)

وقتی نئوویم نصب شد، می‌توانید با تایپ سادهٔ `nvim` (یا `nvim <filename>` برای باز کردن فایلی مشخص) در ترمینالی که چند بخش قبل نصب کردید، آن را امتحان کنید. اگر نئوویم درست نصب شده و روی مسیر (path) باشد، ویرایشگری از نظر دیداری نازیبا می‌گیرید که انگار از چیزی نوشته‌شده در دههٔ ۹۰ فورک شده و قصد صریحش این بوده که شبیه چیزی نوشته‌شده در دههٔ ۷۰ به نظر برسد.

پس، دست‌کم صادق است؟

متأسفانه، اکنون به دام افتاده‌اید. برای نجات‌تان از جست‌وجوی سراسیمهٔ «چگونه از Vim خارج شوم» در گوگل، دستور خروج `Escape` و به دنبالش سه کاراکتر `:q!` و به دنبالش `Enter` است. پس کل دنباله `<Escape>` `<Colon>` `q` `<Exclamation>` `<Enter>` خواهد بود.

جدی می‌گویم، «چگونه از Vim خارج شوم» یکی از سه تکمیل خودکار برتر گوگل برای «How do I exit…​» است. ظاهراً فقط تلویزیون سامسونگ پلاس و حالت تمام‌صفحه در مک‌اواس برای خروج کمتر شهودی‌اند! بعد از این‌که عمیق‌تر وارد مدل ذهنی vim و حالت دستوری (command mode) شویم، می‌فهمیم چرا این افسون کار می‌کند.

|  |  |
| --- | --- |
|  | اگر بخواهید، می‌توانید دستور `<Escape>:Tutor<Enter>` را اجرا کنید تا فایل متنی تعاملی باز شود که می‌توانید هنگام یادگیری مبانی نئوویم آن را بخوانید و ویرایش کنید. توصیه می‌کنم در نقطه‌ای این کار را بکنید، اما الان ممکن است زمان مناسبی نباشد. خیلی چیزها که در آموزش ویم «عادی» هستند با LazyVim متفاوت‌اند (بهتر!). بقیهٔ این کتاب فرض **نمی‌کند** که آموزش را گذرانده‌اید. |

### [۱.۸. نصب LazyVim](#_install_lazyvim)

حالا که نئوویم بالا آمده و اجرا می‌شود، بیایید آن را پیکربندی کنیم تا شبیه چیزی باشد که این قرن توسعه داده شده است.

نصب LazyVim کمی کار با `git` می‌طلبد. چون این کتاب را می‌خوانید، فرض می‌کنم توسعه‌دهندهٔ نرم‌افزارید و در نتیجه تا حدی با `git` آشنا هستید.

دستورهای git برای نصب LazyVim برای سیستم‌عامل‌های مختلف کم‌وبیش یکسان‌اند، هرچند مسیرها و متغیرهای محیطی کمی متفاوت‌اند.

#### [۱.۸.۱. با صفحهٔ تمیز شروع کنید](#_start_with_a_clean_slate)

|  |  |
| --- | --- |
|  | اگر از قبل پیکربندی نئوویم دارید و می‌خواهید LazyVim را بدون از دست دادن پیکربندی موجود امتحان کنید، متغیر محیطی `NVIM_APPNAME=lazyvim` را تنظیم کنید. به بخش `Clone the starter template` زیر بپرید و به‌جای `~/.config/nvim` در `~/.config/lazyvim` کلون کنید. اگر می‌خواهید تغییرات را دائمی کنید، یا `NVIM_APPNAME` را در فایل راه‌اندازی شل‌تان تنظیم کنید یا آن پوشهٔ پیکربندی `lazyvim` را به `nvim` تغییر نام دهید. |

ابتدا، همهٔ داده‌های موجود نئوویم را حذف یا پشتیبان بگیرید. این گام اگر هرگز از نئوویم استفاده نکرده‌اید عمدتاً اختیاری است، اما توصیه می‌کنم مطمئن شوید دایرکتوری‌های زیر حذف یا جابه‌جا شده‌اند:

##### [پاک‌سازی: ویندوز با WSL، مک‌اواس و لینوکس](#_clean_up_windows_with_wsl_macos_and_linux)

دایرکتوری‌های زیر را حذف کنید (یا با `mv` به‌جای `rm -rf` پشتیبان بگیرید):

فهرست ۱. دستورهای پاک‌سازی یونیکس

```text
$ rm -rf ~/.config/nvim
$ rm -rf ~/.local/share/nvim
$ rm -rf ~/.local/state/nvim
$ rm -rf ~/.cache/nvim
```

##### [پاک‌سازی: ویندوز بدون WSL](#_clean_up_windows_without_wsl)

محل پوشه‌های پیکربندی و داده در ویندوز کمی متفاوت است، اما ایده همان یونیکس است. فقط به‌جای ابزارهای پایهٔ یونیکس از دستورهای پاورشل استفاده کنید:

فهرست ۲. دستورهای پاک‌سازی پاورشل

```text
$ Move-Item $env:LOCALAPPDATA\nvim $env:LOCALAPPDATA\nvim.bak
$ Move-Item $env:LOCALAPPDATA\nvim-data $env:LOCALAPPDATA\nvim-data.bak
```

#### [۱.۸.۲. نصب سایر وابستگی‌های توصیه‌شده](#_install_other_recommended_dependencies)

قویاً توصیه می‌کنم `lazygit`، `ripgrep` و `fd` را نصب کنید که توسط LazyVim برای ارائهٔ رفتارهای بهبودیافتهٔ git، جست‌وجوی رشته و جست‌وجوی فایل استفاده می‌شوند. بیشتر مدیران بستهٔ سیستم‌عامل این‌ها را برای نصب بدیهی در دسترس دارند. می‌توانید دستورالعمل‌های نصب مشخص‌تر را در مخازن GitHub مربوطه‌شان پیدا کنید:

- [jesseduffield/lazygit](https://github.com/jesseduffield/lazygit)

- [BurntSushi/ripgrep](https://github.com/BurntSushi/ripgrep)

- [sharkdp/fd](https://github.com/sharkdp/fd)

#### [۱.۸.۳. کلون کردن قالب شروع LazyVim](#_clone_the_lazyvim_starter_template)

از دستور `git clone` استفاده می‌کنید تا قالب شروع (starter template) را دانلود کنید و در دایرکتوری پیکربندی کاربر برای نئوویم کپی کنید، بعد پوشهٔ `.git` را حذف کنید.

استارتر فقط همان است: یک شروع. پس هرگز لازم نیست تغییراتی از این مخزن pull کنید. در عوض، LazyVim به‌روزرسانی خودش و همهٔ افزونه‌هایش را برایتان مدیریت می‌کند. تنها دلیل این‌که استارتر مخزن git است این است که نگهداری آن برای نگه‌دارندگان LazyVim آسان است. از دید شما فقط دارید وضعیت فعلی مخزن را دانلود می‌کنید و لازم نیست دربارهٔ وضعیت گذشته یا آینده بدانید.

##### [کلون مخزن شروع: WSL، مک‌اواس و لینوکس](#_clone_starter_repository_wsl_macos_and_linux)

در سیستم‌های یونیکس، از این دستورها استفاده کنید:

فهرست ۳. کلون استارتر در یونیکس

```text
$ git clone https://github.com/LazyVim/starter ~/.config/nvim
$ rm -rf ~/.config/nvim/.git
```

##### [کلون مخزن شروع: ویندوز بدون WSL](#_clone_starter_repository_windows_without_wsl)

در ویندوز بومی، از این دستورها استفاده کنید:

فهرست ۴. کلون استارتر در پاورشل

```text
$ git clone https://github.com/LazyVim/starter $env:LOCALAPPDATA\nvim
$ Remove-Item $env:LOCALAPPDATA\nvim\.git -Recurse -Force
```

### [۱.۹. داشبورد](#_the_dashboard)

خب، دشوارترین بخش این کتاب را کامل کردید و بالاخره آماده‌اید LazyVim را شروع کنید! از همان دستور ترمینال قبلی استفاده کنید: `nvim`.

هیاهویی از فعالیت می‌بینید وقتی LazyVim همه‌چیز را راه‌اندازی می‌کند و افزونه‌هایی که ضروری می‌داند را دانلود می‌کند. ممکن است ببینید که تعدادی گرامر تری‌سیتر را کامپایل و نصب می‌کند؛ اگر پیامی برای «Show More» دیدید از `G` (یعنی `Shift+g`) برای پرش به انتها استفاده کنید.

وقتی همه‌چیز نصب شد، خلاصه‌ای از افزونه‌های نصب‌شده را داخل پنجره‌ای می‌بینید که توسط افزونه‌ای به نام Lazy.nvim مدیریت می‌شود که به‌زودی بحثش می‌کنیم. فعلاً، وقتی به صفحهٔ Lazy.nvim رسیدید، می‌توانید کلید `q` را بزنید. افزونه این را به‌عنوان «خروج از Lazy.nvim» تفسیر می‌کند و پنجره بسته می‌شود.

حالا می‌توانید داشبورد LazyVim را ببینید که اولین چیزی است که هر بار در آینده LazyVim را شروع می‌کنید خواهید دید. کمی دوستانه‌تر از تجربهٔ نئوویم خارج‌ازجعبه است:

![داشبورد در تم تیره](/images/book/chapter-1/dashboard-dark.png)

شکل ۱. داشبورد LazyVim

همان‌طور که می‌بینید، چندین دستور هست که اجازه می‌دهد با داشبورد با یک کلید تعامل کنید. مهم‌ترین‌شان البته کلید `q` برای خروج است!

بیشتر این گزینه‌ها خودتوضیح‌اند، اما چندتایشان را عمیق‌تر در فصل‌های بعدی بحث می‌کنیم.

### [۱.۱۰. مدیر افزونهٔ Lazy.nvim](#_lazy_nvim_plugin_manager)

وقتی اولین بار LazyVim را باز می‌کنید، برای افزونه‌هایی که برای به‌روزرسانی در دسترس‌اند بررسی می‌کند و نمای کلی در اعلان پیامی می‌دهد که چیزی شبیه این خواهد بود:

![اعلان به‌روزرسانی افزونه‌ها در تم تیره](/images/book/chapter-1/plugin-updates-dark.png)

شکل ۲. اعلان به‌روزرسانی افزونه

چون نئوویم به‌طور پیش‌فرض نسبتاً خیلی ساده است، LazyVim با کلی افزونهٔ مفید آمادهٔ کار عرضه می‌شود. و احتمال خوبی هست که قدیمی باشند چون توسعهٔ افزونه در دنیای نئوویم با سرعت مضحکانه سریعی اتفاق می‌افتد.

در روزگار خیلی قدیم، مدیریت افزونه فرایندی کاملاً دستی بود. در روزگار کمتر قدیم، اما هنوز قدیم، توسط انواع افزونه‌ها مدیریت می‌شد که کار را انجام می‌دادند اما حس می‌شد چیزی کم دارند.

بعد مدیر افزونه‌ای به نام Lazy.nvim آمد که توسط همان شخصی ساخته شد که بعداً LazyVim را ساخت. مدیر افزونهٔ Lazy.nvim را نباید با خود LazyVim اشتباه گرفت، هرچند هر دو توسط همان شخص نگهداری می‌شوند. Lazy.nvim صرفاً مدیر افزونه است، در حالی که LazyVim مجموعه‌ای از افزونه‌ها و پیکربندی‌هاست که با هم عرضه می‌شوند. یکی از آن افزونه‌ها Lazy.nvim است.

Lazy.nvim کلی ویژگی جذاب دارد، برجسته‌تر از همه بارگذاری افزونه‌ها فقط هنگام نیاز (از این رو نام «Lazy» یعنی تنبل) تا ویرایشگرتان در شروع، سرعتی برق‌آسا داشته باشد. همچنین رابط کاربری خوبی برای مدیریت نصب و به‌روزرسانی افزونه دارد.

می‌توانید از داشبورد با فشردن کلید `l` به این رابط دسترسی پیدا کنید که در داشبورد به‌عنوان `Lazy` برچسب خورده است. برچسب احتمالاً باید `Lazy Plugin Manager` باشد تا کمی واضح‌تر شود، اما حالا می‌دانید `Lazy` یعنی چه پس فراموش نمی‌کنید.

اگر فعالانه داشبورد را نمایش نمی‌دهید، می‌توانید مدیر افزونه را هر زمان با ورود به حالت Space نشان دهید. حالت Space را در فصل بعد با جزئیات پوشش می‌دهیم، اما فعلاً: اول مطمئن شوید با بررسی گوشهٔ پایین چپ پنجرهٔ فعال در حالت نرمال (Normal mode) هستید. اگر نه، `Esc` را برای ورود به حالت نرمال بزنید. بعد `Space` را برای ورود به حالت Space بزنید و به دنبالش `l` را برای بالا آوردن مدیر افزونهٔ Lazy.nvim.

(نگران نباشید، همهٔ آن کلیدها ظرف یک هفته طبیعت دوم می‌شوند.)

شکل ۳. مدیر افزونهٔ Lazy.nvim

پنجره‌ای که بالا آمده پنجرهٔ شناور (floating window) نامیده می‌شود. این‌ها را در چند موقعیت مختلف می‌بینید، معمولاً وقتی دادهٔ تعاملی هست که باید با آن کار کنید. این پنجرهٔ شناور خاص مجموعهٔ کلیدهای خودش را دارد. کلیدها در بالا فهرست شده‌اند و توجه کنید که همه‌شان بزرگ‌اند، پس هنگام فراخوانی‌شان باید از کلید `Shift` استفاده کنید.

معمولاً تنها کلید Lazy.nvim که استفاده می‌کنم `S` برای `Sync` است. این معادل اجرای install و clean و update در یک عمل است. تضمین می‌کند نسخه‌های افزونه‌هایی که واقعاً نصب‌اند دقیقاً با آن‌هایی که در پیکربندی LazyVim مشخص شده سازگارند.

پس وقتی اعلان «Plugin Updates» بالا آمد، فقط `Space-l` و بعد `S` را بزنید و صبر کنید همگام‌سازی کامل شود. بعد `q` را برای بستن حالت Lazy.nvim Plugin و پنجرهٔ شناور و بازگشت به کاری که می‌کردید بزنید.

### [۱.۱۱. نکته‌ای دربارهٔ مدیریت دات‌فایل‌ها](#_a_note_on_managing_dot_files)

اگر روی کامپیوترهای مختلف متعددی کار می‌کنید، به‌سرعت می‌بینید که نمی‌خواهید پیکربندی LazyVim را جداگانه روی همه‌شان راه‌اندازی کنید. LazyVim معادل ویژگی «Settings Sync» VS Code را ندارد، هرچند چنین افزونه‌هایی وجود دارند.

جایگزینی که توصیه می‌کنم ذخیرهٔ فایل‌های پیکربندی در مخزن git است. احتمالاً می‌بینید چند فایل دیگر هم هست که می‌خواهید آنجا نگه دارید مثل فایل پیکربندی ترمینال‌تان، `.gitconfig` و `.zshrc` / `.bashrc` / `.config/fish/config.fish` شما.

اگر از GitHub Codespaces استفاده می‌کنید، ممکن است از قبل برخی دات‌فایل‌ها را با git مدیریت کنید. اگر نه، توصیهٔ شخصی من دنبال کردن توصیهٔ مقالهٔ وبلاگی فوق‌العادهٔ [Dotfiles: Best way to store in a bare git repository](https://www.atlassian.com/git/tutorials/dotfiles) از وبلاگ Atlassian است.

پیش از این‌که توزیع‌هایی مثل LazyVim بیایند، خیلی رایج بود که افراد پیکربندی Vim را در مخزن عمومی ذخیره کنند و از یکدیگر ایده قرض بگیرند. این عمل کاملاً نمرده و می‌توانید دات‌فایل‌های خودم را در GitHub در مخزن [dusty-phillips/dotfiles](https://github.com/dusty-phillips/dotfiles) پیدا کنید.

### [۱.۱۲. خلاصه](#_summary)

در این فصل، به‌اختصار دربارهٔ تاریخچهٔ Vim، Neovim و LazyVim و این‌که چرا هنوز مرتبط‌اند بحث کردیم. بعد اهمیت ترمینال‌های شتاب‌گرفته با GPU و Nerd Fonts را پوشش دادیم.

فهمیدیم چگونه نئوویم و وابستگی‌هایش را تحت هر سیستم‌عاملی که استفاده می‌کنید نصب کنیم و در نهایت LazyVim را از قالب شروعش نصب کردیم.

در فصل بعد، دربارهٔ ویژگی اصلی Vim بحث می‌کنیم: ویرایش مُدال، و عمیق می‌شویم در کارهای زیادی که می‌توانید با صفحه‌کلید در LazyVim انجام دهید.
